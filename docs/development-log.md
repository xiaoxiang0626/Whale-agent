# 开发问题与验证日志

本页统一记录开发过程中影响使用、实现或验证的问题，以及解决方案和可核对的指标变化。使用方法和当前 API 规则仍由各自的技术文档维护，本页链接到对应说明。记录不包含密钥、认证缓存或用户业务数据。

## 记录方式

每个需求记录日期、阶段与 PR、问题现象、根因、解决方案、验证命令和结果。没有遇到问题时记录主要验证与能力变化；有未解决问题时说明影响和后续验证方式，不标为已解决。

指标需要说明前后口径和测量方法。测试数量表示用例数量，不代表覆盖率；功能增加不等同于性能提升。当前未建立延迟、吞吐量、内存或 token 成本的可比较性能基线。

## 2026-11-23：模型 API 与环境文件

关联：[模型接口 PR #4](https://github.com/xiaoxiang0626/my-coding-agent/pull/4)。

**问题一：环境文件参数冲突。**初始设计使用 `--env-file` 作为应用参数。实际子进程验证中，Node.js 对该参数进行了启动阶段处理；文件不存在时，进程以退出码 9 结束，应用无法给出预期的配置诊断。应用参数改为 `--env`，由应用显式加载文件。Node.js 自己的 `node --env-file=…` 用法保持独立。

**验证：**CLI 子进程覆盖存在的环境文件、文件不存在、命令行覆盖、已有环境变量优先和帮助模式。文件缺失会显示 `INVALID_CONFIG` 并以退出码 1 结束；错误不回显文件内容。

**问题二：只有密钥仍无法访问真实服务。**本地配置保存后仍包含示例接口域名，调用返回 `NETWORK_ERROR`。分别检查安全的非敏感配置字段和未认证网络连通性，确认 DeepSeek 官方接口可达。将接口地址、模型名和超时改为 DeepSeek 配置，保留密钥字段，实际文本请求返回“连接成功”，退出码 0。真实配置不进入 Git。

**模型接口验证：**认证失败、限流、服务错误、无效 JSON、不完整输出、响应大小、超时与取消均有自动化测试。源码 CLI 与构建后的 CLI 均通过本地 HTTP 服务完成文本请求。接口配置见[模型 API 指南](model-api.md)。

**质量指标：**同一项目的 `pnpm check` 测试数量由 9 项增加至 18 项，类型检查和构建通过。没有据此宣称覆盖率或性能提升。

## 2026-11-23：持续输入与会话上下文

关联：[交互会话 PR #5](https://github.com/xiaoxiang0626/my-coding-agent/pull/5)，阶段 004；实现与阅读顺序见[交互会话技术说明](prs/004-interactive-session.md)。

**使用问题：**单次任务回复后进程退出，用户无法在同一 CLI 会话中继续输入。新增逐行交互界面和独立会话对象，成功问答成对进入内存历史，后续模型请求携带历史。失败、取消与迟到回复不改变此前历史；提供清空、帮助与退出命令。

**实现问题：输入结束后显示提示符导致报错。**构建产物通过真实 DeepSeek 接口验证时，管道输入先结束，第一轮回复返回后仍调用 readline 提示符，触发 `ERR_USE_AFTER_CLOSE`，进程退出码为 1。终端层改为跟踪输入关闭事件，关闭后继续处理已收到的行，但不再重新显示提示符。

**回归验证：**新增确定性测试，在输入关闭后才释放第一轮模型回复，确认第二条已接收输入仍能完成，并且正常退出。其他测试覆盖上下文顺序、清空、失败恢复、并发拒绝、Ctrl+C 取消和退出。

**真实服务验证：**构建后的交互 CLI 使用本地 DeepSeek 配置连续处理两轮消息，第二轮正确返回第一轮设定的暗号；随后完成 `/clear`、`/help` 和 `/exit`，进程退出码为 0。会话内容和密钥均未写入仓库夹具。

**验证限制：**当前工具环境无法创建用于交互检查的伪终端进程，返回 Windows `CreateProcessW` 拒绝访问。已改用显式交互参数和管道验证真实模型调用，并使用 readline 接口测试取消事件。真实终端的自动进入与键盘按键效果仍需在用户终端确认，未把工具限制归为产品缺陷。

## 2026-11-23：全屏终端交互界面

关联：[终端界面 PR #7](https://github.com/xiaoxiang0626/my-coding-agent/pull/7)，阶段 006，分支 `功能/006-终端交互界面`；设计、阅读顺序与验收见[技术说明](prs/006-terminal-interface.md)。

**使用问题与解决：**逐行输出缺少固定输入区、模型状态和可浏览的消息区域。新增 Ink 与 React 全屏终端界面，宽屏显示鲸鱼娘侧栏，普通窗口单栏显示，窄窗口收起边框。`--plain` 保留逐行会话，非终端交互自动使用逐行模式，单次任务保持原有输出。

**字符编辑与显示：**输入按 UTF-16 索引移动会拆开 emoji 和组合字符，长草稿也可能挤出输入框。输入编辑改为 `Intl.Segmenter` 字素索引，用 string-width 计算显示列数，并按光标位置移动水平视口。通过 Ink 定位真实终端光标，为输入法提供候选位置；未自动操作本机输入法候选窗。消息折行与终端控制符清理仅作用于显示，模型历史仍使用原文本。

**翻页问题与解决：**最初到达历史顶部后仍可无限累积偏移，反向翻页需要多次按键才改变显示。将偏移限制在实际可滚动行数内，调整窗口后也使用有效偏移；新增到顶后继续翻页、再向下翻页的回归检查。

**真实终端验证问题与解决：**此前工具通过 Windows PowerShell 别名创建终端时返回 `CreateProcessW` 拒绝访问。本阶段使用 node-pty 直接启动 Node.js，并通过 xterm 解析终端输出，已完成实际伪终端验证。测试夹具曾把未定义的 `CI`、`NO_COLOR` 值传给 node-pty，被序列化为字符串 `undefined`，导致交互检测不符合预期；现仅传递已定义的环境变量。CLI 确认输入和输出均为终端后，显式开启 Ink 交互渲染。

**emoji 夹具问题：**核对缩放前后的完整草稿时，终端模拟器默认字符宽度规则把鲸鱼 emoji 当作一列，导致消息与侧栏坐标混合。按 [xterm 官方说明](https://github.com/xtermjs/xterm.js/blob/master/addons/addon-unicode11/README.md)在测试中加载 Unicode 11 插件，随后按对话区列范围提取内容，完整草稿检查通过。插件类型声明还引用 `@xterm/xterm`，将其显式加入开发依赖后严格类型检查通过。这些包仅供开发验证，不改变产品终端或用户输入。

**安装与清理问题：**pnpm 默认阻止 node-pty 安装脚本并使首次安装返回失败。本项目使用其自带预编译模块，在工作区配置中显式禁止该包安装脚本；`pnpm install --frozen-lockfile` 随后通过，原生模块实测可加载。另发现 Windows ConPTY 在子进程正常退出后仍保留测试进程的输入管道，检查脚本现在在清理阶段显式释放伪终端；脚本随检查结果正常结束，没有强制退出测试进程。

**验证：**`pnpm check` 的 32 项测试、类型检查和构建通过。新增 6 项 TUI 行为测试覆盖布局、中文/emoji/组合字符编辑、缩放保留草稿、历史翻页、失败恢复、取消与卸载。`pnpm test:tui:pty --capture` 使用构建产物验证真实终端自动进入界面、模拟问答、长草稿、三种尺寸、清空、帮助、退出码 0 与备用屏幕恢复。`pnpm start` 验证单次模拟任务和显式逐行会话。预览由此次离线伪终端输出的字符单元格绘制，未包含真实接口数据。

**真实服务：**`pnpm test:tui:pty --live` 显式使用本地 DeepSeek 配置，完成一次固定文本问答，界面显示成功问答轮数 1，并正常退出、恢复备用屏幕。检查脚本不保存真实服务的屏幕内容或密钥。

## 2026-11-23：只读工具与 Agent 循环

关联：[只读 Agent PR #9](https://github.com/xiaoxiang0626/my-coding-agent/pull/9)，阶段 008，分支 `功能/008-只读工具与执行循环`；交付和阅读顺序见[技术说明](prs/008-read-only-agent.md)。

**能力变化：**由单次文本模型调用增加为“模型提出调用、执行只读工具、回传结果、模型继续”的有界循环。提供工作区、模型请求上限和关闭工具的 CLI 参数，终端显示工具摘要。成功历史保留完整工具消息和调用 ID，问答轮数独立计数。

**协议问题与解决：**原适配器只接受 `finish_reason: stop`。接入函数调用后增加 `tool_calls` 校验与协议字段转换；根据 [DeepSeek 思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)保留工具请求所需的 `reasoning_content`，覆盖后续回传，终端不显示推理正文。真实服务已经完成一次读取临时随机标记、据结果回答的循环。

**文件访问处理：**使用维护中的 `ignore` 解析逐层忽略规则，结合相对路径、受保护名称、真实路径、链接检查和打开后文件标识验证。文本字节、行数和返回字符数均有限制。路径错误、无效 JSON、二进制或过大文件作为固定工具诊断回传；取消停止后续工作。此处提供工具级检查，不称为进程沙箱。

**输入恢复问题与解决：**新增进度渲染后，原有取消回归测试暴露了输入监听在禁用与启用之间重新注册的间隙。输入组件改为保持键盘监听，通过当前禁用状态过滤按键；请求刚结束后的输入不再依赖监听重新挂载。取消、重试和完整 TUI 检查通过。

**验证：**`pnpm check` 的 42 项测试、类型检查和构建通过，覆盖多工具消息、调用 ID、上下文、循环限制、权限、忽略规则、链接、文本限制与 CLI。构建后的离线 CLI 实际读取源码并回传结果，`.env` 请求返回 `PATH_DENIED`。真实伪终端检查覆盖工具读取、摘要、三种尺寸与正常退出。`pnpm test:agent:live` 使用本地 DeepSeek 配置，仅发送临时夹具，完成 4 次模型请求，其中一个实际 `read_file` 调用。

## 2026-11-23：修改预览与确认写入

关联：[修改预览与确认 PR #10](https://github.com/xiaoxiang0626/my-coding-agent/pull/10)，阶段 009，分支 `功能/009-修改预览与确认写入`；[阅读顺序与交付](prs/009-confirmed-editing.md)。

**实现与问题：**提案先生成 diff，用户输入 `/apply` 才写入。使用 `diff` 生成有界预览，保留 BOM、CRLF 和结尾换行，避免读取时归一化导致无关文件变化。确认时重新校验摘要和权限，临时文件刷新后替换，拒绝覆盖预览后的用户修改。已确认操作独立记录，解决实际写入成功但后续模型失败时历史丢失的问题。

**终端验证问题：**帮助新增确认命令后超过当前消息视口，原 PTY 检查等待被滚出视口的旧文案而超时。断言改为检查当前显示的确认命令，保持真实交互与退出检查。显示层统一过滤控制序列，diff 和回复中的控制字符不作为终端指令执行。

**验证与指标：**`pnpm check` 的 47 项测试、类型检查和构建通过；`pnpm test:tui:pty --capture` 在临时工作区验证预览、确认写入、三种尺寸与屏幕恢复。`pnpm test:editing:live` 完成 7 次真实 DeepSeek 请求，调用 list_files、read_file、propose_file，再确认并检查临时文件。相同首条消息只声明工具定义：只读 552 prompt token，增加修改工具后 724，增加 172；不包含工作区 system 提示。测试由 42 增至 47，直接运行依赖由 5 增至 6，没有据此宣称性能提升。

## 2026-11-23：命令确认与测试反馈

关联：[命令确认与测试反馈 PR #11](https://github.com/xiaoxiang0626/my-coding-agent/pull/11)，阶段 010，分支 `功能/010-命令确认与测试反馈`；[交付与阅读顺序](prs/010-confirmed-commands.md)。

**实现：**模型只生成命令提案，用户 `/run` 后才启动。程序、参数、目录和超时预先展示；实际退出码、合并输出和截断标记回传。非零退出也继续模型分析；取消保留实际结果。进程无法确认清理时报告 unknown，阻止后续文件修改和命令，禁止直接重试。

**问题与解决：**Windows 的包装器与可执行文件解析不同，使用 cross-spawn 处理 `.cmd`，避免自写 shell 拼接。缺失程序的回归测试发现 Windows 包装器会先输出本地化系统诊断；启动失败结果现在清空该输出，使用固定失败类别。命令子进程采用少量环境白名单，模型 Key 不继承；已知 Key 从结果中精确脱敏。截断前额外保留密钥长度的缓冲，避免恰好跨截断点的完整密钥漏过匹配。

**验证与指标：**`pnpm check` 的 51 项测试、类型检查和构建通过，真实 PTY 完成命令预览、确认、退出码显示、三种尺寸与退出恢复。`pnpm test:commands:live` 完成 5 次真实 DeepSeek 请求，显式确认后只运行临时 Node 测试，退出码 0；相同首条消息工具定义从 724 增至 939 prompt token，增加 215。测试从 47 增至 51，直接运行依赖从 6 增至 7，新增 cross-spawn。没有性能提升结论。

**限制：**前台命令按用户账户运行，不能限制其文件或网络访问；不支持守护进程，不承诺终止脱离进程组的后台任务。Windows 非 UTF-8 输出可能乱码。完整日志与重启恢复在下一阶段实现。
